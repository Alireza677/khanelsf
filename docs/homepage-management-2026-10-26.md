# اصلاح تجربه مدیریت Homepage

تاریخ: ۲۰۲۶-۱۰-۲۶

## علت و مسیر داده اثبات‌شده

قابلیت قبلی انتخاب Homepage در checkout حاضر وجود دارد:

```text
ManageSiteSettings → تب عمومی → homepage_page_id
  → form.getState → metadata گروه general، نوع select
  → SettingsService::set → settings.updateOrCreate(key=homepage_page_id)
  → SettingsService::homepagePageId → همان جدول و همان key
  → HomeController → Page::published()->whereKey(id)
  → view('page') → همان رندر بلوک‌های برگه
```

کلید settings در Schema موجود unique است. بنابراین انتخاب جدید همان رکورد را به‌روزرسانی می‌کند، نه اینکه برای چند برگه وضعیت Homepage جداگانه ثبت کند. ذخیره تنظیمات، هیچ فراخوانی update روی Page ندارد.

در سورس پیش از این اصلاح، `HomeController` با شناسه مثبتِ `homepage_page_id` از نامک و `Page.template` مستقل بود. در صورت شناسه null، برگه منتشرشده با نامک `home` و View قدیمی `home` را مصرف می‌کرد. getter شناسه، مقادیر نامعتبر مانند `0`، عدد منفی و متن را نیز null می‌کرد؛ در نتیجه این مقادیر صریحِ خراب به fallback می‌رسیدند.

مشاهده Production مبنی بر درست‌شدن `/` پس از تغییر slug به home، با فعال‌بودن fallback سازگار است. از سورس نمی‌توان تعیین کرد مقدار واقعی خالی/نامعتبر بوده، نسخه مستقر قدیمی بوده، ذخیره فرم با خطا مواجه شده، یا کش محیط پاسخ قدیمی داده است. هیچ‌یک از این احتمالات به‌عنوان علت قطعی سایت واقعی اعلام نمی‌شود.

ابهام مدیریتی قطعی در `PageResource` بود: فیلد قالب، ستون جدول و فیلتر جدول `home` را «صفحه اصلی» می‌نامیدند. اما `HomeController` و `PageController` از مقدار template برای تعیین Homepage استفاده نمی‌کنند. انتخاب قالب home هیچ تنظیمی در settings نمی‌نویسد. مقدار template در داده Page و snapshot رونوشت‌ها نگهداری می‌شود؛ بنابراین حذف یا تبدیل خودکار داده قدیمی انجام نشد. مصرف‌های UI و رونوشت بررسی شدند؛ انتخاب Homepage به آنها وابسته نیست.

## اصلاح محدود

### فرم و فهرست برگه‌ها

- برگه جدید یا برگه‌ای با قالب default/landing فقط «پیش‌فرض» و «لندینگ» را برای انتخاب دارد. اعتبارسنجی سمت سرور نیز ثبت جدید `home` را رد می‌کند.
- برگه‌ای که از قبل template=home دارد، آن مقدار را با عنوان «قالب قدیمی (home)» و گزینه غیرفعال می‌بیند. ذخیره ویرایش‌های دیگر مقدار موجود را حفظ می‌کند. تغییر اختیاری به default/landing مجاز است؛ هیچ backfill یا تبدیل خودکاری انجام نمی‌شود.
- عنوان Legacy در ستون و فیلتر قالب نیز اصلاح شد؛ فیلتر برای پیدا کردن برگه‌های قدیمی باقی است.
- در فرم ویرایش برگه صریحاً منتخب، پیام «این برگه به‌عنوان صفحه اصلی سایت انتخاب شده است.» و لینک مدیریت انتخاب نمایش داده می‌شود. برگه‌ای که صرفاً نامک home یا قالب home دارد، این نشان را دریافت نمی‌کند.
- Tabs موجود تنظیمات، شناسه پایدار و پشتیبانی Query String گرفته است تا لینک نشان مستقیماً تب عمومی را باز کند: `?tab=site-settings-general-tab`.

### ذخیره Homepage

- همان `homepage_page_id` و همان SettingsService استفاده می‌شود؛ کلید یا جدول جدیدی اضافه نشده است.
- گزینه‌ها و اعتبارسنجی سمت سرور از scope موجود `Page::published()` استفاده می‌کنند. برگه draft یا زمان انتشار آینده برای انتخاب جدید پذیرفته نمی‌شود.
- هنگام جایگزینی برگه قبلی، Action تأیید استاندارد Filament نام برگه قبلی و جدید را نشان می‌دهد. تا تأیید، هیچ‌یک از تنظیمات فرم نوشته نمی‌شوند. انصراف تنظیمات ذخیره‌شده را حفظ می‌کند.
- اگر سایت هنوز از برگه منتشرشده با نامک home به‌عنوان fallback استفاده کند، جایگزینی آن با برگه دیگر نیز تأیید می‌خواهد. انتخاب همان برگه یا ذخیره بدون تغییر انتخاب، تأیید اضافی نمی‌خواهد.
- پاک‌کردن انتخاب صریح موجود نیز پیام تأیید لغو انتخاب دارد. پس از تأیید، مقدار خالی به معنی بازگشت مجاز به رفتار Legacy است.
- در زمان تأیید، فرم دوباره اعتبارسنجی می‌شود؛ برگه‌ای که در فاصله نمایش پیام تا تأیید از انتشار خارج شده باشد، قابل ثبت نیست.
- ذخیره انتخاب، slug/template/content/blocks و updated_at برگه را تغییر نمی‌دهد.

### رفتار عمومی و کش

در `HomeController` یک guard اضافه شد: مقدار غیرخالیِ کلید که شناسه مثبت معتبر نیست، 404 می‌دهد. شناسه مثبتِ برگه حذف‌شده، draft، وضعیت غیرمنتشر یا انتشار آینده نیز از همان query انتشار فعلی به 404 می‌رسد. فقط کلید غایب یا مقدار خالی/null اجازه fallback دارد. قواعد انتشار، View استاندارد Page، Custom HTML/CSS/JS و SEO تغییر نکرده‌اند.

`SettingsService::set` پیش از updateOrCreate ورودی کش همان کلید را حذف می‌کند؛ الگوریتم کش تغییر نکرد. تست‌ها مسیر کش فعال را با subclass آزمایشی اجرا و قبل و بعد هر تست پاک می‌کنند. خواندن پس از ذخیره با کش گرم، پاسخ GET و بارگذاری دوباره فرم، و خواندن سرد از settings بررسی شده است. این آزمایش، صحت کش CDN یا همگامی چند worker در محیط واقعی را اثبات نمی‌کند.

## فایل‌های بررسی‌شده

علاوه بر فایل‌های تغییرکرده، این مسیرها برای اثبات قرارداد بررسی شدند:

- `app/Services/SettingsService.php`: get/many/set، getter شناسه و invalidation همان کلید؛
- `app/Http/Controllers/PageController.php` و `app/Models/Page.php`: مسیر مستقیم و scope انتشار؛
- `app/Filament/Resources/PageResource/Pages/EditPage.php` و `CreatePage.php`: ذخیره فرم و رونوشت؛
- `app/Services/Revisions/PageRevisionSnapshot.php`: حفظ template در snapshot؛
- `resources/views/filament/pages/manage-site-settings.blade.php`: فرم فعلی و اتصال submit به save؛
- `database/migrations/2026_05_30_000000_create_cms_tables.php`: unique بودن settings.key؛
- بخش home در `database/seeders/DatabaseSeeder.php`: داده Legacy؛ Seeder اجرا یا تغییر داده نشده است؛
- `phpunit.xml` و `.env.testing`: استفاده از SQLite در حافظه؛
- پیاده‌سازی نصب‌شده Select، Tabs و Actions در vendor برای استفاده از API موجود Filament.

## فایل‌های تغییرکرده

| فایل | دلیل |
| --- | --- |
| `app/Filament/Resources/PageResource.php` | رفع ابهام قالب، حفظ مقدار Legacy، اعتبارسنجی گزینه‌های جدید، نشان و لینک Homepage |
| `app/Filament/Pages/ManageSiteSettings.php` | تأیید جایگزینی پیش از ذخیره، اعتبارسنجی برگه منتشرشده و لینک‌پذیری تب عمومی |
| `app/Http/Controllers/HomeController.php` | جلوگیری از fallback برای مقدار صریح خراب |
| `tests/Feature/HomepageManagementTest.php` | تست‌های مدیریت، Legacy، تأیید/انصراف، رندر و کش فعال |
| `tests/Feature/HomepageHeaderIntegrationTest.php` | تطبیق helper ذخیره آزمایشی با مرحله تأیید جدید؛ assertionهای قبلی حفظ شدند |
| `README.md` و همین گزارش | توضیح قرارداد مدیریتی و نتیجه بررسی |

هیچ Migration، تغییر Schema، تغییر واقعی دیتابیس، تغییر Page Builder، Block System، Navigation، Template Runtime یا SEO انجام نشده است. رفتار نامک‌های رزروشده در لینک‌های قبلی نیز بازطراحی نشده است.

## تست‌ها

پیش از اصلاح، هفت سناریوی هدفمند اجرا شد: شش شکست و یک موفقیت. شکست‌ها نبود نشان و تأیید، گزینه گمراه‌کننده قالب، و fallback برای مقدار صریح متن/صفر/منفی را نشان دادند. شناسه مثبتِ ناموجود از قبل 404 می‌داد و تست آن موفق بود.

اجرای نهایی: **۴۵ تست، ۳۵۷ assertion، همگی موفق**:

```powershell
$env:APP_ENV='testing'
$env:DB_CONNECTION='sqlite'
$env:DB_DATABASE=':memory:'
$env:DB_URL=''
$env:CACHE_STORE='array'
php -d memory_limit=512M vendor/bin/phpunit `
  tests/Feature/HomepageManagementTest.php `
  tests/Feature/HomepageHeaderIntegrationTest.php `
  tests/Feature/SettingsAdminPageTest.php `
  tests/Feature/PageRevisionHistoryTest.php `
  tests/Feature/PageHeadingWarningTest.php --no-progress
```

پوشش مرتبط:

- انتخاب برگه با نامک غیر home، جایگزینی، حفظ تنها یک رکورد تنظیم و رندر انتخاب جدید؛
- استقلال default/landing از تعیین Homepage و بدون تغییرماندن داده کامل Page هنگام انتخاب؛
- حفظ Custom HTML، CSS و JS و برابری رندر با مسیر مستقیم در تست قبلی؛
- نشان برگه منتخب و لینک تب عمومی، بدون نشان روی برگه صرفاً دارای نامک/قالب home؛
- رد انتخاب جدید قالب home و حفظ مقدار موجود Legacy هنگام ذخیره و رندر عادی؛
- تأیید، انصراف، بدون ذخیره‌ماندن سایر فیلدها پیش از تأیید، و نبود پیام اضافی برای انتخاب بدون تغییر؛
- رد برگه منتشرنشده در ثبت جدید و اعتبارسنجی مجدد در صورت draft شدن برگه هنگام بازبودن تأیید؛
- fallback فقط برای نبود انتخاب، و 404 برای انتخاب صریحِ خراب، شناسه ناموجود، draft، وضعیت غیرمنتشر، زمان انتشار آینده و برگه حذف‌شده؛
- خواندن/نوشتن با کش فعال و گرم، بارگذاری دوباره فرم و خواندن دوباره از settings پس از پاک‌کردن کش آزمایشی؛
- سازگاری تست‌های قبلی SettingsAdmin، رونوشت برگه، هشدار تیتر و اتصال هدر.

اجرای ترکیبی اولیه با سقف پیش‌فرض ۱۲۸ مگابایت متوقف شد؛ اجرای نهایی فقط برای فرایند PHPUnit سقف ۵۱۲ مگابایت داشت و مصرف گزارش‌شده آن ۱۳۶ مگابایت بود. تنظیم حافظه برنامه یا Production تغییر نکرده است. دو assertion اولیه درباره عدم تغییر Page نیز پیش از مقایسه نهایی با بارگذاری تازه Fixture یکسان‌سازی شدند تا تفاوت نوع boolean خام Factory با عدد ذخیره‌شده دیتابیس، تغییر داده تلقی نشود.

`php -l` برای هر پنج فایل PHP تغییرکرده، `pint --test` روی همان فایل‌ها و `git diff --check` موفق بودند. تست مرورگر یا بررسی بصری Production انجام نشده است. این اجرای هدفمند جایگزین اجرای کل suite پروژه نیست.

## بررسی لازم پس از استقرار

1. تطبیق نسخه مستقر با این checkout و مشاهده مقدار واقعی `homepage_page_id` پس از ذخیره از پنل؛ اصلاح فعلی داده واقعی را نخوانده یا منتقل نکرده است.
2. انتخاب برگه منتشرشده‌ای با نامک غیر home از تنظیمات عمومی، تأیید جایگزینی و مقایسه `/` با آدرس مستقیم آن؛ هیچ نیازی به تغییر نامک یا قالب برای این کار نیست.
3. بررسی نمایش نشان فقط روی برگه منتخب و بازشدن تب عمومی از لینک آن؛ بررسی بصری Modal تأیید و رفتار انصراف.
4. بررسی خطاهای اعتبارسنجی/ذخیره احتمالی، مجوزهای پنل، کش مرورگر/CDN/سرور، workerها و ریدایرکت احتمالی `/` در سایت واقعی.
5. بررسی اجرای مجاز CSS/JS بلوک Custom HTML و Layout واقعی در مرورگر؛ تست PHP اجرای مرورگر و CSP محیط را تأیید نمی‌کند.

نتیجه تست آزمایشی به معنی تأیید عملکرد Production نیست.
