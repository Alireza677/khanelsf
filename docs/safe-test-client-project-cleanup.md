# پاک‌سازی امن یک ClientProject آزمایشی

این تغییر فقط ابزار نگهداری سورس را اضافه می‌کند. هیچ فرمان حذف روی پایگاه‌داده محلی یا سرور اجرا نشده است. دسترسی به داده‌های واقعی سرور وجود نداشته و پروژه‌ای برای حذف انتخاب نشده است.

## فایل‌ها

- `app/Console/Commands/CleanupTestClientProject.php`: فرمان Artisan با dry-run پیش‌فرض، تأیید صریح و بررسی پس از حذف.
- `app/Services/TestClientProjectCleanup.php`: بررسی گراف واقعی وابستگی‌ها، محافظ مالی و schema، تراکنش و مدیریت محدود فایل.
- `app/Services/ClientProjectCleanupPlan.php`: اعتبارسنجی مالکیت، fingerprint، تأیید هویت و ترتیب دقیق حذف.
- `tests/Unit/ClientProjectCleanupPlanTest.php`: تست‌های مستقل از پایگاه‌داده.
- `docs/safe-test-client-project-cleanup.md`: همین راهنما.

مدل، migration یا رفتار معمول حذف پروژه تغییر نکرده است. فرمان از مسیر خودکار حذف Filament، تغییر وضعیت، صدور/لغو صورت‌حساب یا سرویس‌های lifecycle استفاده نمی‌کند. برای استثنای صریح پاک‌سازی داده آزمایشی، فقط Query Builder با شرط دقیق هر رکورد و کنترل تعداد حذف در این فرمان استفاده می‌شود؛ محافظ‌های مدل‌های immutable در استفاده عادی پابرجا هستند.

## یافته‌های سورس و مرز مالکیت

| داده | رابطه / قید واقعی | رفتار فرمان |
|---|---|---|
| `client_projects` | `customer_id` به مشتری؛ RESTRICT | فقط یک شناسه صریح پروژه |
| `client_project_plan_versions` | پروژه و نسخه عرضه؛ RESTRICT، تاریخچه immutable | نسخه‌های توافق متعلق به همان پروژه حذف می‌شوند؛ نسخه عرضه حفظ می‌شود |
| `client_project_cycles` | پروژه CASCADE؛ نسخه توافق RESTRICT | حذف صریح پس از فرزندان، بدون تکیه بر CASCADE پروژه |
| `client_project_cycle_commitments` | دوره، توافق و نوع خروجی؛ RESTRICT | فقط تعهدات همان دوره/توافق؛ نوع خروجی حفظ می‌شود |
| `client_project_work_items` | پروژه، دوره و تعهد؛ RESTRICT | همه شناسه‌های والد باید متعلق به گراف انتخاب‌شده باشند |
| `client_project_work_item_user` | pivot کار و کاربر؛ RESTRICT | فقط ردیف pivot حذف می‌شود؛ کاربر حفظ می‌شود |
| `client_project_work_item_activity` | pivot کار و فعالیت؛ RESTRICT | هر دو سمت باید متعلق به پروژه و همان دوره باشند |
| `client_project_work_item_events` | کار RESTRICT؛ actor کاربر با SET NULL | فقط رخدادهای همان کار؛ actor حفظ می‌شود |
| `client_work_item_deliveries` | کار RESTRICT؛ ارسال‌کننده کاربر | فقط نسخه‌های همان کار |
| `client_work_item_reviews` | تحویل RESTRICT؛ بررسی‌کننده کاربر | فقط بررسی‌های همان تحویل |
| `client_delivery_files` | metadata فایل خصوصی، تحویل RESTRICT | metadata همان تحویل؛ فایل فیزیکی به‌صورت پیش‌فرض حفظ می‌شود |
| `client_cycle_reports` | دوره RESTRICT، snapshot immutable | فقط گزارش‌های همان دوره |
| `client_project_activities` | پروژه RESTRICT؛ دوره SET NULL؛ اجراکننده و خدمت مشترک | فعالیت‌های پروژه بدون claim مالی حذف می‌شوند؛ خدمت/کاربر حفظ می‌شوند |
| `invoices` | دوره SET NULL، مشتری RESTRICT | وجود هر وضعیت، حتی draft یا cancelled، مانع حذف است |
| `invoice_items` | پروژه/فعالیت SET NULL | هر قلم مرتبط مانع حذف است |
| `invoice_activity_claims` / `invoice_cycle_claims` | claim مالی با CASCADE | وجود claim، حتی با رابطه مالی ناقص، مانع حذف است؛ claim حذف نمی‌شود |
| وضعیت `invoiced` یا `invoiced_at` دوره | نشانه مالی در lifecycle فعلی | حتی بدون ردیف صورت‌حساب، مانع حذف است |
| `media`، `media_usages`، `revisions` و سایر روابط polymorphic | رابطه نوع/شناسه، بدون FK به ClientProject | اگر به گراف انتخاب‌شده اشاره کنند، فرمان متوقف می‌شود تا جداگانه بررسی شوند؛ رسانه مشترک حذف نمی‌شود |

سورس فعلی برای صورت‌حساب خدمات مدل یا جدول Payment مستقل ندارد؛ پرداخت صورت‌حساب با وضعیت `paid` و `paid_at` در `InvoiceLifecycle` ثبت می‌شود. پرداخت فروشگاه در `orders.payment_status` قرار دارد و رابطه‌ای با ClientProject ندارد. سفارش‌ها و تمام داده‌های مشتری/کاربر/خدمت/بسته/نسخه عرضه/نوع خروجی مشترک حفظ می‌شوند. هر FK یا ستون وابستگی اضافی به شناسه‌های دامنه که در schema مستقر کشف شود، مانع حذف است؛ جدول مالی ناشناخته پاک نمی‌شود.

مبنای بررسی شامل migrationهای foundation پروژه/فعالیت، invoicing و cycle billing، و Phase 1–3 قرارداد، WorkItem، تحویل خصوصی، بررسی و گزارش است. سرویس‌های توافق، تولید/مدیریت کار، تحویل/بررسی، cycle و `InvoiceLifecycle` و محافظ‌های immutable نیز بررسی شده‌اند.

## حفاظ‌های اجرا

۱. فقط یک عدد صحیح مثبت و canonical پذیرفته می‌شود؛ صفر، مقدار منفی، لیست، wildcard، مقدار اعشاری و شناسه ناقص رد می‌شوند.

۲. نبود `--execute` یعنی dry-run. dry-run فقط SELECT/metadata و تراکنش خواندن دارد؛ هیچ ردیف، فایل یا manifest نمی‌نویسد. identity پروژه/مشتری، نوع تحویل، تعداد همه جدول‌های وابسته، صورت‌حساب و claimها، وضعیت پرداخت، مسیر دقیق فایل‌ها و blockerها نمایش داده می‌شوند.

۳. اجرا به تکرار شناسه پروژه، شناسه مشتری و fingerprint دقیق گزارش نیاز دارد. fingerprint تمام رکوردهای انتخاب‌شده و زمینه بررسی را پوشش می‌دهد. تغییر پروژه، توافق، کار، تحویل، فعالیت، مشتری یا ارجاع فایل پس از dry-run، تأیید قبلی را نامعتبر می‌کند.

۴. تمام بررسی‌ها داخل تراکنش با `FOR UPDATE` تکرار می‌شوند. ردیف‌های دارای ارتباط متقاطع از مسیرهای دیگر هم جست‌وجو می‌شوند؛ برای نمونه کار پروژه دیگر با دوره/تعهد منتخب و فعالیت پروژه دیگر با دوره منتخب. هر ناسازگاری مالکیت مانع حذف کل گراف است.

۵. جدول‌های دارای FK ورودی به گراف، ستون‌های وابستگی دامنه و روابط polymorphic بررسی می‌شوند. نبود FK ضروری، trigger روی جدول هدف، رابطه ناشناخته، چند schema مبهم، FK بین schema/databaseها یا خاموش‌بودن `FOREIGN_KEY_CHECKS` مانع حذف است. این ابزار FK را غیرفعال نمی‌کند.

۶. اجرای واقعی محدود به MySQL با جدول‌های هدف/مالی InnoDB یا PostgreSQL با schema قابل بررسی و بدون table prefix است. SQLite و driverهای دیگر برای اجرای حذف پذیرفته نیستند. schema ناقص یا metadata غیرقابل بررسی با خطا متوقف می‌شود؛ ابزار migration یا اصلاح خودکار ندارد.

۷. ترتیب حذف صریح: metadata فایل → review → delivery → event → pivot مسئولان و فعالیت‌ها → WorkItem → commitment و report → activity → cycle → plan version → همان پروژه. برای هر ردیف، شناسه و کلیدهای مالکیت مشخص در WHERE قرار می‌گیرند؛ تعداد حذف باید دقیقاً یک باشد. هر اختلاف یا خطای FK تراکنش را rollback می‌کند. هیچ جدول مشترک یا مالی در فهرست حذف وجود ندارد.

۸. نبود بعضی وابسته‌ها طبیعی است و از آن‌ها عبور می‌شود. پروژه ناموجود در dry-run گزارش می‌شود؛ اجرای دوباره روی پروژه حذف‌شده تغییری ایجاد نمی‌کند. بررسی دقیق وابسته‌های قبلی با manifest انجام می‌شود، چون فقط نبود پروژه به‌تنهایی اثبات پاک‌شدن همه وابسته‌های قبلی نیست.

## اجرای دستی روی سرور

ابتدا این سورس را با روند معمول خود به سرور منتقل کنید. فرمان به‌صورت خودکار از `app/Console/Commands` با `withCommands()` فعلی ثبت می‌شود. از ریشه همین پروژه Laravel و با محیط/اتصال صحیح سرور اجرا کنید. هیچ migration جدیدی لازم نیست.

در فرمان‌های زیر، `PROJECT_ID` را فقط با شناسه پروژه آزمایشی انتخاب‌شده، `CUSTOMER_ID` را با شناسه مشتری گزارش، `FINGERPRINT` را با رشته دقیق چاپ‌شده و `MANIFEST_PATH` را با مسیر دقیق چاپ‌شده توسط اجرای واقعی جایگزین کنید. این نام‌ها placeholder هستند؛ شناسه‌ای برای سرور فرض نشده است.

### ۱. بررسی پیش از حذف

```bash
php artisan help client-project:cleanup-test
php artisan client-project:cleanup-test PROJECT_ID --dry-run
```

فرمان بدون `--dry-run` هم همان گزارش فقط‌خواندنی است:

```bash
php artisan client-project:cleanup-test PROJECT_ID
```

عنوان پروژه، شناسه و نام مشتری، نام اتصال و database، نوع تحویل، تعدادها و همه blockerها را بررسی کنید. فرمان نمی‌تواند از نام پروژه تشخیص دهد که داده واقعاً آزمایشی است؛ انتخاب و تأیید شما لازم است. با وجود هر رکورد مالی یا blocker، اجرا رد می‌شود و گزینه‌ای برای دورزدن آن وجود ندارد.

پیش از حذف واقعی، backup قابل بازیابی همان database را با ابزارهای معمول سرور تهیه کنید. از تغییر هم‌زمان این پروژه، صدور صورتحساب، reconciliation و ارسال فایل برای آن در طول عملیات جلوگیری کنید. هنگام انتخاب حذف فیزیکی فایل‌ها، نویسندگان فایل و workerهای مربوط نیز باید متوقف باشند.

### ۲. حذف تأییدشده، با حفظ فایل‌های فیزیکی

```bash
php artisan client-project:cleanup-test PROJECT_ID --execute --confirm-project=PROJECT_ID --confirm-customer=CUSTOMER_ID --fingerprint=FINGERPRINT
```

این فرمان فقط پس از عبور از تمام بررسی‌ها، گراف انحصاری پایگاه‌داده را حذف می‌کند. فایل‌ها باقی می‌مانند و مسیرهای آن‌ها در manifest خصوصی محفوظ است.

اگر حذف فایل‌های فیزیکی همان پروژه را هم صریحاً می‌خواهید، **به‌جای فرمان بالا** این فرمان را در اجرای اول استفاده کنید:

```bash
php artisan client-project:cleanup-test PROJECT_ID --execute --confirm-project=PROJECT_ID --confirm-customer=CUSTOMER_ID --fingerprint=FINGERPRINT --delete-files
```

### ۳. بررسی پس از حذف

مسیر manifest پیش از اولین DELETE چاپ می‌شود و پس از commit نیز دوباره نمایش داده می‌شود:

```bash
php artisan client-project:cleanup-test PROJECT_ID --verify-manifest="MANIFEST_PATH"
php artisan client-project:cleanup-test PROJECT_ID --dry-run
```

بررسی manifest کاملاً فقط‌خواندنی است. نبود تک‌تک شناسه‌های ثبت‌شده، pivotها، حضور مشتری مشترک و وضعیت فایل‌ها را بررسی می‌کند. استفاده مجدد یا تغییر مالکیت یک شناسه، به‌عنوان رکورد باقی‌مانده گزارش می‌شود. در حالت `--delete-files` باقی‌ماندن فایل نیز موجب شکست verification می‌شود. در حالت حفظ فایل، حضور آن‌ها مطابق انتخاب قبلی است. dry-run دوم باید نبود پروژه را گزارش کند؛ جایگزین verification manifest نیست.

## فایل خصوصی و محدودیت تراکنش/فایل‌سیستم

- فقط disk فعلی `service_deliveries` با driver محلی و visibility خصوصی پذیرفته می‌شود. مسیر باید دقیقاً مطابق مسیر writer فعلی، `deliveries/{delivery_id}/{uuid}`، و شناسه delivery باید متعلق به گراف تأییدشده باشد.
- مسیر دارای traversal، مسیر مطلق، زیرشاخه اضافی، disk نامعتبر، checksum نامعتبر یا ارجاع مشترک موجب توقف می‌شود. تعداد ارجاع مسیر در کل metadata فایل‌ها بررسی می‌شود، حتی اگر disk دیگری داشته باشد.
- در حذف اختیاری فیزیکی، root باید مستقل از root دیگر diskهای محلی باشد. پس از commit، نبود ارجاع جدید دوباره بررسی می‌شود؛ symlink در مسیر رد می‌شود و containment، اندازه و SHA-256 با metadata تأییدشده تطبیق داده می‌شوند.
- تنها همان فایل با `unlink` حذف می‌شود. هیچ `deleteDirectory`، حذف بازگشتی، glob یا حذف root/پوشه مشترک وجود ندارد. فایل ناموجود نتیجه «already absent» دارد.
- پیش از اولین DELETE، manifest با نام یکتا در `storage/app/private/client-project-cleanup` ذخیره، flush و sync می‌شود. manifest دارای امضای HMAC با `APP_KEY`، شناسه‌ها، predicates و metadata فایل است؛ متن یادداشت‌ها و snapshot کامل قرارداد در آن ذخیره نمی‌شود. دسترسی پوشه/فایل به‌ترتیب 0700/0600 تنظیم می‌شود. APP_KEY برای verification باید ثابت بماند.
- DB و فایل‌سیستم تراکنش مشترک ندارند. فایل فیزیکی پیش از commit حذف نمی‌شود؛ بنابراین rollback پایگاه‌داده نباید فایل را از بین ببرد. توقف فرایند پس از commit یا خطای unlink می‌تواند فایل orphan باقی بگذارد. manifest پیش از حذف پایدار شده تا شناسه‌ها و مسیر دقیق از دست نروند.
- حذف فیزیکی در مقابل writer خارج از کنترل برنامه کاملاً اتمی نیست؛ توقف نویسندگان فایل هنگام `--delete-files` ضروری است. اگر این شرط را نمی‌توانید فراهم کنید، فایل‌ها را حفظ کنید. هیچ پاک‌سازی بازگشتی خودکار برای orphanها ارائه نشده است.
- اگر ارتباط حین commit قطع شد، ابتدا manifest را verify کنید؛ صرف مشاهده خطا اثبات rollback نیست. اگر DB حذف شده ولی فایل باقی مانده، فرمان حذف DB را تکرار نکنید. فایل باقی‌مانده باید جداگانه با همان مسیر دقیق و بررسی مالکیت/عدم اشتراک/محتوا رسیدگی شود.
- manifest سند موفقیت commit نیست؛ سند هدف‌های برنامه‌ریزی‌شده است. نتیجه واقعی با `--verify-manifest` مشخص می‌شود. verification روی storage ناموجود یا تنظیمات ناسازگار با خطا متوقف می‌شود.

## بررسی انجام‌شده در محیط سورس

۸ تست هدفمند، ۹۹ assertion، موفق بودند. تست‌ها فقط ساختار فرمان و آرایه‌های حافظه را بررسی می‌کنند: شناسه نامعتبر، تأیید هویت و fingerprint، رکوردهای مالی، مالکیت متقاطع، روابط nested/pivot، مسیر خصوصی/اشتراک، ترتیب حذف و وابسته‌های ناقص. از `PHPUnit\Framework\TestCase` استفاده شده و برنامه Laravel، PDO، migration یا پایگاه‌داده راه‌اندازی نشده است.

```bash
php vendor/bin/phpunit tests/Unit/ClientProjectCleanupPlanTest.php
```

بررسی syntax PHP و Pint نیز انجام شده است. مجموعه کامل تست و هیچ اجرای عملی حذف یا اتصال به database برای این کار انجام نشده است. اجرای واقعی تراکنش، schema مستقر و فایل‌سیستم سرور در این محیط قابل آزمایش نبوده‌اند؛ dry-run و verification سرور برای همین منظور فراهم شده‌اند.
